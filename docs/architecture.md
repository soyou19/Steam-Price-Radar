## 一句话架构

> 用**滚动扫描**发现候选 → 用**候选队列**排优先级 → 用 `appdetails` **逐个精确校验** →
> 变更走**事件总线** → 经 **SSE** 推给浏览器，同时**原子落盘**。

核心难点不是"抓"，而是**在 1 请求/秒的配额下，先问最可能是限免的那批商品**。

## 动手前的实测结论

### 1. Steam 官方没有"限时免费"列表

| 接口 | 实测结果 |
| --- | --- |
| `/search/results/?specials=1` | 抽样 15,000+ 条，折扣范围 **10%–90%**，**零个** 100% 折扣，也不含永久免费条目 |
| `/search/results/?maxprice=free` | 约 **64,640** 条，但**无法区分**永久免费与限时免费 |
| `/search/results/?maxprice=free&specials=1` | 恒返回 `total_count=0`（Steam 直接排除该组合） |
| `/api/featuredcategories` | specials 只有 10 条，且无免费条目 |

### 2. 列表页的价格信号不可信

- `discount_original_price`：永久免费（CS2 / Apex）与限时免费**都不渲染**；
- `data-price-final`：同类商品表现不一致 —— 永久免费的 CS2 返回 `10300`（占位原价），
  Apex 返回 `0`。

所以**不能**用"原价 > 0 却出现在免费列表"来判断限时免费。

### 3. 唯一权威来源是 `appdetails`，但它一次只能查 1 个 appid

```
GET /api/appdetails?appids=730,570      ->  HTTP 400  null   ❌
GET /api/appdetails?appids=730          ->  HTTP 200         ✅
```

`price_overview` 的语义（已实测确认）：

| 场景 | `is_free` | `price_overview` | 判定 |
| --- | --- | --- | --- |
| 永久免费（F2P） | `true` | `null` | `f2p` |
| 限时免费入库 | `true` | `final=0, discount_percent=100` | `keep` |
| 免费周末 | `false` | 看着像普通折扣 | `weekend`（**需读 `package_groups`**，见下） |
| 普通付费/折扣 | `false` | `final>0` | `discount` |
| 限免已结束 | `false` | `final>0` | 触发 `ended` |

另外：`filters=price_overview` 用在免费游戏上会返回
`{"appids":{"N":{"success":true,"data":[]}}}` —— 空数组，不能当作"没有价格"以外的含义。

### 4. 商店页 HTML 已经不能用来判价

现在的购买区是 **JS 动态渲染**的，抓下来的 HTML 里只有 `game_area_purchase goes here`
占位符。所以"抓商店页解析价格"这条路彻底失效，只能走 `appdetails`。

## 五个数据源如何互补

```
                ┌─────────────────────────────────────────────┐
                │  A. steam-catalog  免费候选集滚动扫描        │
                │     maxprice=free，游标分页，约 6.4 万条      │
                │     产出：候选 appid 队列 + 条目             │
                └───────────────────┬─────────────────────────┘
                                    │ 登记候选（分诊 + 跳过试玩版）
                ┌───────────────────▼─────────────────────────┐
                │  B. steam-discounts  折扣清单扫描            │
                │     specials=1，约 1.57 万条，带价格与折扣    │
                │     产出："曾促销"appid 集合 + 高折扣参考数据 │
                └───────────────────┬─────────────────────────┘
                                    │
                ┌───────────────────▼─────────────────────────┐
                │  C. steam-details  精确价格校验              │
                │     appdetails：price_overview +             │
                │     package_groups.subs（识别免费周末）      │
                └───────────────────┬─────────────────────────┘
                                    │
                ┌───────────────────▼─────────────────────────┐
                │  D. steam-spotlight  商店精选位              │
                │     featuredcategories 的 spotlight          │
                │     产出：免费周末（候选集里根本没有）        │
                └───────────────────┬─────────────────────────┘
                                    │
                ┌───────────────────▼─────────────────────────┐
                │  E. gamerpower     第三方限免聚合            │
                │     补充激活码 / 站外领取类信息              │
                └─────────────────────────────────────────────┘
```

对应的源码：

| 源名 | 文件 | 是否"权威" | 作用 |
| --- | --- | --- | --- |
| `steam-catalog` | `src/sources/steamCatalog.js` | ❌ 分页来源 | 发现候选；另含评测回填任务 |
| `steam-discounts` | `src/sources/steamDiscounts.js` | ❌ 分页来源 | 折扣清单 + 曾促销集合 |
| `steam-details` | `src/sources/steamDetails.js` | ✅ **权威** | 逐个确认免费形态 |
| `steam-spotlight` | `src/sources/steamSpotlight.js` | ✅ **权威** | 免费周末 / 限时体验 |
| `gamerpower` | `src/sources/gamerpower.js` | ✅ **权威** | 站外领取 / 激活码 |

> **"权威"很关键**：只有权威来源才能判定某个条目"已下架/已结束"。
> 分页滚动来源**永远不能**据此判定结束 —— 一次翻页里没看到某条目，
> 只说明它不在这一页，不代表它消失了。早期实现没有区分这一点，导致大量误判 `ended`。

> **D 是必需的，不是锦上添花**：免费周末是订阅制限时体验（例如 F1® 25 通过 EA Play 免费玩），
> 它**不会进入 `maxprice=free` 候选集** —— 实测 F1® 25 完全不在那 6.4 万条列表里。
> 所以只靠 A+B+C 永远发现不了免费周末。

## 候选队列与分诊

候选队列是本项目的核心机制。流程：

1. **登记**：扫描免费列表时，每个 appid 进队（按 appid 去重，重复登记取更强的信号）；
2. **排序**：优先级 = `曾出现在促销索引中`（基本可确定是付费商品）> `评测数多`；
3. **消化**：每轮取 `WATCHLIST_BATCH` 个，用 `appdetails` 精确校验，校验完出队；
4. **免检期**：已校验的 appid 在 TTL 内不再请求（周期见[数据治理](#数据治理什么该复核)）。

### 分诊：不是每个候选都值得花一次配额

启动时有数万候选，但绝大多数是"完全没有信号"的冷门条目 ——
没有评测、没有价格提示、也从未出现在促销索引里，查了几乎必然是永久免费小游戏。

所以会做一次**分诊**：

```
候选队列分诊：共 40979 个，需校验 9890 个，本次新跳过 31089 个（省下约 4.3 小时配额）
```

被跳过的仍**记录在队列中**，一旦出现更强信号（曾促销 / 有评测 / 有价格）会**自动重新激活**，
不会永久丢失。界面"采集状态"里可以看到：
`待校验候选：41068 个（其中需花配额校验 9979 个）`。

### 试玩版识别

免费候选集里 Demo / 试玩版 / 序章占比极高，它们不是用户要找的"限时免费完整游戏"。
`src/model.js` 的 `isDemo` 用**完整词**匹配（`试玩版` / `试玩demo` / `体验版` / `序章` / `序幕`），
并带一个负向保护（命中 `激活|领取|兑换|序列号|key` 就不算试玩版）。

> 早期用 `/试玩/` 匹配，结果因为字符重叠把"激活码"也判成了试玩版（`试` + `活`），
> 把有效条目藏了起来。这个 bug 有回归测试保护。

## 免费周末的判定

实测 F1® 25 正在免费周末时，`appdetails` 返回的是：

```jsonc
{
  "is_free": false,
  "price_overview": { "final": 17360, "discount_percent": 30 },   // 看着就是个 30% 折扣
  "package_groups": [{
    "subs": [
      { "option_text": "F1® 25 - EA Play - 免费",
        "is_free_license": true, "price_in_cents_with_discount": 0 },  // ← 真正的免费信号
      { "option_text": "《F1® 25》：2026赛季版 - ¥248.00 ¥173.60",
        "is_free_license": false }
    ]
  }]
}
```

只读 `price_overview` 会把它误判成「30% 折扣」。因此 `src/sources/steamDetails.js`
的 `classifyFree()` 规则是：

| 条件 | 判定 |
| --- | --- |
| `is_free=true` 且无 `price_overview` | 永久免费 `f2p` |
| `is_free=true` 且有 `price_overview.final=0` | 限时活动（按文案分 `weekend` / `keep`） |
| **`is_free=false` 但 `subs` 里有 `is_free_license: true`** | **免费周末 / 限时体验** `weekend` |
| `is_free=false` 且 `discount_percent > 0` | 折扣 `discount` |
| `is_free=false` 且无折扣 | 付费 `paid`（**永不返回给前端**） |

> 不能只看 `is_free_license`：CS2 / Dota 2 这类永久免费游戏的 `subs` 里也有它。
> 区分点正是 **`is_free=false` + 存在免费 sub**。
>
> 另外，`paid` 这个类型是后来补的：早期把"付费且无折扣"也记成 `discount`，
> 导致"高折扣"里混进一堆 `-0%` 的条目、统计数字虚高。

## 评测数据从哪来

**来源**：免费候选集的列表页本身就带评测信息（`data-tooltip-html`）。

```
中文：特别好评<br>此游戏的 1,412,376 篇用户评测中有 89% 为好评。
英文：Very Positive<br>86% of the 2,613,842 user reviews …
```

`src/parse.js` 的 `parseReviewStats` 两种文案都支持。

### 两个实测踩过的坑

1. **存档漏字段**：`reviewSummary` / `reviewPercent` 一度没写进精简存档
   （只有 `reviewCount` 写了），重启后评价结果与好评率**全部丢失**，
   覆盖率从应有的 ~90% 掉到 16%。已修，并加了往返测试。

2. **Steam 只在候选集前段返回评测**：实测 `start=12000` 时 100 条里 99 条有评测，
   `start=20000` 时只剩 3 条。而主扫描游标是单调推进的，等它绕回开头太久。
   因此加了**独立的评测回填任务**（`steamCatalog.backfillReviews()`）：
   用单独游标从头扫（上限 14,000 条），只补字段、不推进主游标、不登记候选，
   每页间隔 800 ms 主动让出配额，遇到限流会退避重试（最多容忍 3 次连续错误，
   避免像早期那样"一次 HTTP 429 直接中断，回填只跑了 15 页"）。

**代价**：越靠后的冷门条目越可能没有评测数据。这是上游数据源的客观限制。

## 实时推送

```
数据源轮询 ──► store.upsert() ──► 变更检测(diff)
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
              event 事件                      条目状态更新
        (discovered/became_free/          (价格、折扣、活跃状态)
         price_drop/ended/updated)
                    │                               │
                    └──────────► SSE Hub ◄──────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
            event: 具体变更帧               item: 变更 key 列表帧
        (前端弹通知/toast/动态栏)        (前端只重拉这些条目)
```

SSE 帧类型：

```
event: hello     首次连接（含服务端时间与统计快照）
event: event     具体变更：discovered / became_free / price_drop / ended / updated
event: item      发生变更的条目 key 列表（前端据此增量重拉，而不是整页重载）
: ping           心跳保活注释
```

**去抖动**：条目变更按 700 ms 批量合并推送；事件帧即时推送。
前端只重拉变更的那几个 key —— 这是页面能在数万条规模下保持流畅的关键前提之一。

## 持久化与不重复抓取

### 重启后数据还在吗？在。

| 内容 | 是否持久化 | 说明 |
| --- | --- | --- |
| 抓到的条目 | ✅ 全部 | 精简存档，重启后逐条恢复 |
| 扫描游标 | ✅ | 重启后从上次位置继续，不从头扫 |
| 待校验候选队列 | ✅ | 重启后接着排 |
| 已校验标记 | ✅ | `lastVerifiedAt` 随条目一起存 |
| 事件记录 | ✅ 最近 800 条 | 有上限，不会无限增长 |
| 前端已加载的分页 | ✅（浏览器内） | 切走再切回不重置 |

落盘策略：变更后 **45 秒去抖动**写入，另外**每 60 秒强制落盘一次**，
所以长时间运行后即使立刻重启也不会丢掉大段进度。写入用
**临时文件 + rename** 的原子方式，随时可以直接备份。

### 不重复抓取

1. **同一条目不会重复入队** —— 候选队列按 appid 去重。
   实测：连续扫描同一页 3 次，新增候选依次为 `100 / 0 / 0`。
2. **已校验过的 appid 进入"免检期"**，期间不再请求 `appdetails`。
3. **前端切走再切回不重新加载** —— `bootstrap()` 区分两种模式：
   `reset:true` 只在首次加载时清空并重置分页；切回/SSE 重连用 `reset:false`
   **合并**服务端快照，只更新有变化的条目，保留分页深度与滚动位置。

> 早期实现里 `bootstrap()` 无条件 `state.items.clear()` + `resetPaging()`，
> 于是每次切回标签页都丢掉已加载内容、跳回第一屏、重新加载图片。有回归测试。

## 数据治理：什么该复核

| 类型 | 处理方式 | 复核周期 | 配置项 |
| --- | --- | --- | --- |
| **永久免费（F2P）** | **只读一次，不再复核** | 不复核 | `F2P_RECHECK_MS=0` |
| 高折扣 | 会到期，需定期确认 | 6 小时 | `DISCOUNT_RECHECK_MS` |
| 限时免费 / 免费周末 | 随时可能结束 | 15 分钟 | 代码内固定 |

永久免费的数量以万计，周期性复核它们会吃掉几乎全部配额而几乎不产生新信息 ——
这是刻意的取舍，不是遗漏。

## 为什么需要一个启动器

**代理环境变量必须在 Node 进程启动前就存在。** 在脚本内部赋值（哪怕模块顶层、
任何 `fetch` 之前）**依然无效**：

```
shell:   NODE_USE_ENV_PROXY=1 + HTTPS_PROXY=...   -> HTTP 200 / 约 300ms   ✅
runtime: 同样两个变量在脚本里赋值                  -> UND_ERR_CONNECT_TIMEOUT ❌
```

（`curl` 经同一代理 200/270 ms，排除了代理本身的问题。）

所以不能用"入口里先设变量再动态 import"的方案，而是由 `scripts/run.js`
这个启动器读 `.env`、算出代理变量，**在 `spawn` 子进程时通过 env 传入**。
子进程用 `stdio: 'inherit'`，日志直接透传到终端。这条约束有测试保护。

### 相关的两个坑

| 坑 | 表现 | 解决 |
| --- | --- | --- |
| Node 不读取系统代理 | `UND_ERR_CONNECT_TIMEOUT`（根本没走到加速器） | 设置 `PROXY_URL` 并开启 `NODE_USE_ENV_PROXY` |
| Node 不信任系统证书 store | `UNABLE_TO_VERIFY_LEAF_SIGNATURE`（MITM 自签证书） | 用 `npm start` 启动（带 `--use-system-ca`） |

**这两个开关都是较新才加入 Node 的**，所以启动器会先判断版本：

- `--use-system-ca` —— v22.15.0 / v23.8.0 引入；
- `--use-env-proxy`（等价于 `NODE_USE_ENV_PROXY=1`）—— v22.21.0 引入。

判断逻辑在 `src/net.js` 的 `proxyFeatureSupport()`。旧版本上启动器**不会**盲目注入
`--use-system-ca`（那会让子进程以 `bad option` 直接退出），而是打印明确的升级告警。
详见 [环境依赖](requirements.md#二node-版本要求)。

> 代价说明：多了一个 Node 进程（启动器只转发参数与环境，常驻后几乎不耗资源）。
> 若直连可用、不需要加速器，可以直接 `npm run start:direct`。

## 性能

数据规模会持续增长（免费候选集约 6.4 万条），因此性能是硬约束。实测过的瓶颈与修复：

| 问题 | 实测证据 | 修复 |
| --- | --- | --- |
| 页面卡死、无法响应 | 抓取时每 700 ms 一批 SSE（可达数百 key），每次都 `innerHTML` 重建 **1200 张卡片**；Chrome CPU 采样显示主线程 **72% 时间耗在渲染** | 分页渲染（默认 120 张 + 滚动加载）、`requestAnimationFrame` 合并 + 500 ms 限流、增量请求限并发 6 并去重 |
| `store.active()` 慢 | 3 万条时 **45 ms**（比较函数里反复调用评分函数，约 60 万次） | 先算一次排序键（Schwartzian transform）+ 结果缓存 → **5.2 ms** |
| 落盘阻塞事件循环 | 存档 10.45 MB / 3 万条时 `JSON.stringify` **199–446 ms** 且是同步的，每 60 秒触发一次，期间所有 HTTP 与 SSE 停摆 | 为每条缓存序列化片段，落盘只重序列化**变更过的**条目，成本从 O(全部) 降到 O(变更) |
| `/api/items` 偏慢 | 同一请求内两次调用 `store.active()`，还计算昂贵分组统计 | 复用一次排序结果、高频接口跳过分组统计 → **14–34 ms** |

浏览器实测对比（同一份自然负载，Chrome headless + CDP）：

| 指标 | 旧渲染实现 | 修复后 |
| --- | --- | --- |
| DOM 节点数 | 42,289 | 2,474 |
| 渲染卡片数 | 3,232 | 120 |
| 主线程滞后 p99 | 28 ms | 9 ms |
| 最差单次阻塞 | 203 ms | 94 ms |

首页加载也做了改造：不再一次拉 1200 条，而是**首屏先取 480 条**立刻可交互，
再后台按 `offset` 分页把所有已存数据持续拉进来
（实测 21,490 条约 10 秒读完，之后主线程回落到 6–9 ms）。

> 注：`JSON.stringify` 本身无法异步化，只能通过缩小存档与降低频率来控制其影响。
> 序列化缓存带来一个必须遵守的不变量：**任何修改条目或候选的地方，都要让其序列化缓存失效**。
> 目前覆盖 `upsert` / `markEnded` / `endPass` / `remove`，并有回归测试。

性能验证工具（`bench/`，需要真实浏览器）：

```bash
node bench/browser-perf.js 25     # 真实浏览器主线程阻塞测量
node bench/cpu-profile.js 25      # V8 CPU 采样，定位热点函数
node bench/ab-perf.js 35          # 与 bench/baseline.html 旧实现对照
```

`bench/baseline.html` 是为对照保留的**旧渲染实现**（全量渲染 + 每次重建 + 无限并发），
仅用于性能回归对比，不属于产品功能。

## 一次真实的数据丢失事故

**现象**：运行一段时间后重启服务，条目数从 3 万掉到 1.6 万，数据"消失"了。

**原因**：为了压缩存档体积，当时采用了"只保留有价值的条目、丢弃冷门 F2P"的策略。
但**扫描游标是落盘的，被丢弃的条目不是** —— 重启后游标已经越过那些条目、
不会回头重扫（游标会环绕，但要整整一圈），于是它们永久消失。
更糟的是整个过程完全静默，界面上看不出任何异常。

**修复**：**全部条目一律持久化**，体积改用编码方式压缩
（`compactRecord` 缩短字段名、候选队列改紧凑数组），而不是靠丢数据。另补两道防护：

- `peakItems` 记录历史最高条目数；当前值明显低于峰值时**启动即告警**，
  界面"采集状态"里也会显示"较峰值少 N 条"；
- `worthPersisting()` 保留为显式开关并带注释：**若将来确需裁剪，必须同时回退游标**。

**结论**：存档可以压缩，但**游标推进与持久化必须保持一致**，否则一定丢数据。

### 体积是怎么压下来的（都不丢数据）

| 手段 | 说明 |
| --- | --- |
| 字段名缩写 | `reviewCount` → `r`、`finalPrice` → … |
| 可推导字段不存 | `url` / `image` 能由 appid 推出来 |
| 候选队列用数组 | 5 元素定长数组替代对象 |
| 冗余字段不持久化 | `tags`、长描述等 |
| 事件有上限 | 只留最近 800 条 |

3 万条时的存档构成：`items` 83.8% · `candidates` 11.2% · `events` 3.9% · `seenSpecials` 1.1%。
