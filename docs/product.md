# 产品说明

## 一句话

**Steam 限免雷达**把散落在 Steam 商店各处的"限时免费 / 免费周末 / 限免激活码"聚合成一个
可筛选的网页，新内容通过 SSE **主动推送**到浏览器（并有桌面通知与 Webhook）。

零第三方依赖，本地一条命令跑起来，数据存在自己的机器上。

## 它解决什么问题

Steam **没有提供任何"限时免费"列表接口**。这不是没找到，而是实测确认的：

| 尝试过的接口 | 实测结果 |
| --- | --- |
| `/search/results/?specials=1` | 约 15,714 条，折扣范围只有 **10%–90%**，抽样 15,000+ 条**零个** 100% 折扣，也不含永久免费条目 |
| `/search/results/?maxprice=free` | 约 **64,640** 条，但**无法区分**永久免费与限时免费 |
| `/search/results/?maxprice=free&specials=1` | 恒返回 `total_count=0`（Steam 直接排除这个组合） |
| `/api/featuredcategories` | specials 只有 10 条，且没有免费条目 |
| 商店页 HTML | 购买区已改为 **JS 动态渲染**，抓下来的 HTML 里只有 `game_area_purchase goes here` 占位符 → 靠 HTML 判价彻底失效 |

所以任何"Steam 限免聚合"都必须自己**逐个商品去问**，而这条路有两个残酷约束：

1. 唯一权威接口 `appdetails` **一次只能查 1 个 appid**（传多个直接 HTTP 400）；
2. Steam 对它有**限流**（实测触发 429，需降到约 1000 ms/请求才恢复）。

这个项目要做的就是：在这两个约束下，用有限的请求配额，**优先问最可能是限免的那些商品**，
并把结果实时呈现出来 —— 换句话说，核心不是"抓"，而是**配额调度与候选分诊**。

## 内容类型

界面上的每种类型都有明确的判定依据，不是猜的：

| 类型 | 判定依据 | 含义 |
| --- | --- | --- |
| **限时免费入库**（`keep`） | `is_free=true` 且有 `price_overview.final=0` | 限时领取、**永久入库**，过期就没了 |
| **免费周末**（`weekend`） | `is_free=false` **且** `package_groups[].subs[].is_free_license=true` | 订阅制限时体验，到期即收回 |
| **永久免费**（`f2p`） | `is_free=true` 且无 `price_overview` | F2P 游戏，**不是限免**，仅收录便于浏览 |
| **高折扣**（`discount`） | `discount_percent > 0` | 折扣参考（含 100% 折扣，若出现） |
| **免费激活码**（`key`） | 第三方聚合源（GamerPower） | 站外领取 / 激活码类信息 |
| ~~付费无折扣~~（`paid`） | `is_free=false` 且无折扣 | **永不返回**，只是校验过程的副产品 |

### 免费周末为什么单独一条路

免费周末是**订阅制限时体验**（例如 F1® 25 通过 EA Play 免费玩），
它**不会进入 `maxprice=free` 候选集** —— 实测 F1® 25 完全不在那 6.4 万条里。

而且它在 `appdetails` 里长得像一个普通折扣：

```jsonc
{
  "is_free": false,
  "price_overview": { "final": 17360, "discount_percent": 30 },  // 看着就是"30% 折扣"
  "package_groups": [{
    "subs": [
      { "option_text": "F1® 25 - EA Play - 免费", "is_free_license": true },  // ← 真信号在这
      { "option_text": "《F1® 25》：2026赛季版 - ¥248.00 ¥173.60", "is_free_license": false }
    ]
  }]
}
```

所以只读 `price_overview` 会**完全漏掉免费周末**（这是本项目踩过的一个真实坑）。
现在它只能从商店**精选位**（`featuredcategories` 的 spotlight）发现，并单独开了一个数据源。

> 也不能只看 `is_free_license`：CS2 / Dota 2 这类永久免费游戏的 `subs` 里同样有它。
> 区分点正是 **`is_free=false` + 存在免费 sub**。

## 功能一览

### 聚合与实时

- **五个数据源互补**：免费候选集扫描、促销索引、`appdetails` 精确校验、商店精选位、GamerPower。
- **SSE 主动推送**：新发现 / 转为免费 / 降价 / 限免结束 / 信息更新，五类事件即时推到页面。
  断线由浏览器 `EventSource` 自动重连，页面显示连接状态（绿=推送中 / 黄=连接中 / 红=重连）。
- **桌面通知**：只在"刚刚限免"与"新的激活码/免费周末"时提醒；
  永久免费游戏首次收录**不打扰**（否则会刷屏）。
- **Webhook**：`WEBHOOK_URL` 可推到 Discord / Slack / 自定义 JSON 接口。
- **实时动态栏**：时间倒序展示所有变更事件，点击直达商店页。

### 筛选与浏览

- **统计条覆盖全部类型**（限时免费 / 免费周末 / 免费激活码 / 永久免费 / 高折扣参考 / 收录总数），
  每张卡片**可点击直接筛选**；数字为 0 时弱化显示，一眼看出"这个类型现在真的没有"。
- **评测数据**：每张卡片显示 Steam 的评测档位、好评率与评测数，例如 `特别好评 89% (141.2万)`，
  并按档位配色。
- **评测筛选**：按档位（好评如潮 / 特别好评 / 多半好评 / 褒贬不一 / 差评）与评测数下限
  （≥100 / ≥1千 / ≥1万 / ≥10万）筛选。
- **折扣 / 价格区间筛选**：筛选按钮上直接标着**真实条数**（来自 `/api/facets` 的实际分桶），
  所以不会出现"点了没结果"的空区间；区间可叠加。
- **关键词搜索**：游戏名 / AppID / 描述。**类型 / 来源 / 排序**（按价值 / 最新 / 折扣深度 / 价格 / 名称）。
- **试玩版过滤**：Demo / 试玩版 / 序章 / 体验版默认隐藏（可切换）。
- **采集状态面板**：各数据源健康度、HTTP 请求统计、限流器当前间隔、待校验候选数。

### 数据可靠

- **重启不丢**：条目、扫描游标、候选队列、事件、关注清单全部原子落盘并恢复。
- **不重复抓取**：候选按 appid 去重；已校验的进"免检期"（**永久免费只读一次，不再复核**）。
- **按类型分周期复核**：永久免费不复核、折扣 6 小时、限免/免费周末 15 分钟。
- **数据陈旧可见**：长时间抓不到数据时，`/api/status` 的 `freshness` 与页面顶部提示条
  会明确说明"数据可能不是最新的"以及是哪些源在失败。

### 性能

在 3 万条规模下实测：

| 指标 | 结果 |
| --- | --- |
| 页面加载 21,490 条后的主线程滞后 | **6–9 ms**，全程可交互 |
| `store.active()`（排序 + 过滤） | **5.2 ms**（优化前 45 ms） |
| `/api/items` 服务端耗时 | **14–34 ms** |
| 渲染卡片数 | 120（DOM 约 2,474 节点） |

详见 [架构说明](architecture.md#性能)。

## 界面说明

### 统计条

```
限时免费 0 · 免费周末 1 · 免费激活码 25 · 永久免费 37,343 · 高折扣参考 4 · 收录总数 37,388
```

点任意一张卡片即按该类型筛选。数字为 0 的会弱化显示 —— 这是有意设计的：
"限时免费 0"是一个**有效信息**（现在真的没有），比隐藏起来更有用。

### 高折扣参考 + 区间筛选

选中"高折扣参考"后自动展开折扣区间与价格区间两条筛选，每个区间按钮上带真实条数：

```
折扣区间：10–20% 56 · 20–30% 125 · 30–40% 76 · 40–50% 53 · 50–60% 134
          60–70% 73 · 70–80% 132 · 80–90% 86 · 90–100% 50
价格区间：¥0–10 62 · ¥10–25 233 · ¥25–50 294 · ¥50–100 142 · ¥100–200 48 · ¥200–500 6

当前 785 条折扣
  → 点 80–90%        => 135 条
  → 再叠加 ¥0–10     =>  37 条
```

> 分桶用**左闭右开** `[lo, hi)`，否则边界值会被相邻两桶重复计数
> （这个 bug 是测试抓出来的：价格桶计数之和曾经大于总数）。


## 它不做什么（已知局限）

请务必了解这几点，它们不是缺陷，而是**上游数据源的客观限制**：

1. **发现限免有延迟，冷启动需要时间。**
   Steam 不给限免列表，每个候选都必须逐个确认（1 appid/请求，且被限流到约 1 请求/秒）。
   首轮产生数千候选，**刚启动时列表里几乎全是永久免费游戏**，需要跑一段时间才会收敛。
   进度在"采集状态"面板可见。

2. **永久免费（F2P）数量庞大，它们不是限免。**
   6.4 万条候选里绝大多数是 F2P 与试玩版。项目把它们收录在案便于浏览，
   但别把"永久免费 37,343"当成"有 37,343 个限免"。

3. **免费周末只能从商店精选位发现**，因此覆盖度取决于 Steam 精选位的实时内容
   （实测通常只有个位数活动）。

4. **第三方来源（GamerPower）覆盖度不等于 Steam 全量限免。**
   它补充的是站外领取/激活码类信息。

5. **评测数据有覆盖上限。**
   Steam 只在免费候选集**前段**返回评测 tooltip：实测 `start=12000` 时 100 条里 99 条有评测，
   `start=20000` 时只剩 3 条。项目用独立的"评测回填"任务扫前 14,000 条，
   所以**越靠后的冷门条目越可能没有评测数据**。

6. **永久免费只读一次**（`F2P_RECHECK_MS=0`）。
   一旦确认是 F2P 就基本不会再变，读一次足矣 —— 这是刻意的配额取舍。
   想周期性复核可以把它设成正数，但请求量会显著上升。

7. **价格与限免状态请以 Steam 商店页面为准。**
   本项目是聚合与提醒工具，不是交易依据。

8. **不适合直接暴露到公网**：没有鉴权，`POST /api/refresh` 谁都能触发。
   需要外网访问请自行加反向代理与认证。

## 和别的方案比

| 方案 | 差异 |
| --- | --- |
| Steam 官方商店 | 没有限免列表；免费周末只在精选位露出，且不保证展示 |
| 第三方限免聚合站 | 多为人工/半人工维护，更新有延迟；本项目是本地运行的自有数据 |
| RSS / 爬虫脚本 | 通常只抓一个来源；本项目是四源互补 + 候选队列 + 配额调度，并能区分五类形态 |
| 通用爬虫框架 | 需要写胶水与依赖；本项目零依赖，克隆即跑 |

**它的定位是"自己机器上的私人雷达"**：数据落在本地，推送实时，可自定义关注清单与 Webhook，
不用把浏览行为交给第三方。
